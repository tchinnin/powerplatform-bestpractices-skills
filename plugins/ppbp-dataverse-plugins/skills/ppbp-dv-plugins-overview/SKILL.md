## Official skill

No official Microsoft skill covers plug-in authoring (IPlugin, Custom APIs, the PAC CLI plug-in workflow). Two parts of the official `dataverse` plugin are relevant, so load both before the skills of this plugin:

- `dataverse:dv-overview` sets the registration rule: the first registration goes through the Web API, later updates through `pac plugin push`.
- `dataverse:dv-connect` owns connection setup and PAC CLI authentication.

If the `dataverse` plugin is not installed, **strongly recommend the user install it** before proceeding.

## Connection

- **The dev environment is described in `.env.dev`** at the repo root, which `ppbp-init` creates. Whatever tool registers plug-ins, it targets that environment and nothing else.
- **The Web API uses the Azure CLI token** (`az login`, with `--tenant <TENANT_ID>` when the account spans several tenants).
- **`pac plugin push` uses the active PAC CLI profile** unless it is given an environment explicitly. Never rely on whatever the profile happens to point to.
- Before any change, confirm the target URL, the `az` account and the pac profile with the user.

## Repository layout

```
<repo-root>/
├── .env.dev                              # dev environment descriptor — the only target of registrations
└── plugins/
    └── <PluginName>/                     # One subfolder per Dataverse plug-in project
        ├── <PluginName>.csproj           # Scaffolded by pac plugin init
        ├── PluginBase.cs                 # Generated base class
        └── Models/                       # Early-bound classes (generated — never edit by hand)
```

- **Each plug-in project lives in its own subfolder.** Never place `.csproj` files directly under `plugins/`.
- **Scaffold every new project with `pac plugin init`** — never create one by hand.
- **If the project defines its registrations as code**, the tool's file sits in the project folder, next to the `.csproj`, in that tool's own format. Commit it with the code.

## Global plug-in principles

1. **Always extend `PluginBase`** and override `ExecuteDataversePlugin`. Never implement `IPlugin.Execute` directly in a `pac plugin init` project.
2. **Use early-bound classes** generated by `pac modelbuilder build`, never late binding (`entity["attribute"]`). The generated `Models/` are build output: **never hand-edit them; always regenerate** when the schema changes.
3. **Never use `ColumnSet(true)`** in any Retrieve or image configuration. It bypasses column security and wastes bandwidth.
4. **Declare all working variables inside `ExecuteDataversePlugin()`.** Dataverse reuses plug-in instances, so instance fields accumulate state across calls.
5. **Version every release, and never change the major or minor version of a registered assembly.**
   - Bump the build or revision part of `AssemblyVersion` and `FileVersion` before every release. A solution update may not recognize a changed assembly whose fully qualified name, which includes the version, is unchanged.
   - A major or minor change makes it a *different* assembly on import, and existing steps keep pointing to the old one.
6. **Prefer a plug-in package over a plug-in assembly** for new projects: it carries dependent assemblies and needs no signing. Keep assembly registration for existing projects.
7. **Registrations follow the same rules, whatever tool applies them.**
   - Packages, steps, images and Custom APIs are registered only in the dev environment, and every component lands in its unmanaged solution. UAT and prod receive them through the managed solution (`ppbp-alm-pipelines`).
   - The user sees and confirms the exact change before it is applied.
   - Nothing is deleted automatically. Deleting a step or an image needs an explicit double confirmation.
   - Prefer a reproducible, version-controlled definition of the registrations over clicks in the Plugin Registration Tool. One implementation of this: the `dataverse-as-code` marketplace (`dvac-plugins`).

## Anti-patterns (DO NOT DO)

| Anti-pattern | Correct approach |
|---|---|
| Storing state in instance fields | Declare all variables inside `ExecuteDataversePlugin()` |
| Late binding (`entity["attribute"]`) | Use early-bound classes from `pac modelbuilder build` |
| Hand-editing a generated early-bound class in `Models/` — overwritten on the next regeneration and diverges from the live schema. | Never edit generated classes; re-run `pac modelbuilder build` to regenerate. |
| `ColumnSet(true)` anywhere | Always specify the exact columns needed |
| Creating plugin projects by hand | Always scaffold with `pac plugin init` |
| Registering steps, images or Custom APIs by hand with no recorded definition, or outside the dev unmanaged solution | Keep a reproducible definition of the registrations, applied to dev's unmanaged solution |
| Running `pac plugin push` against whatever environment the pac profile points to | Pass the `.env.dev` environment explicitly, after confirming it with the user |
| Registering in UAT/prod, or in a managed solution | Register in dev's unmanaged solution, then promote through the pipeline |

## Skill boundaries

This skill covers plug-in domain orientation and repository layout. It does not cover:

- Registration procedure (first registration through the Web API, then `pac plugin push`) → `dataverse:dv-overview`
- Project scaffolding, versioning, build → `ppbp-dv-plugin-build`
- Step plugin execution pipeline, images → `ppbp-dv-step-plugin`
- Custom API design and implementation → `ppbp-dv-custom-api`
- Dataverse schema design → `ppbp-dv-metadata-overview`
- Connection setup and PAC CLI authentication → `dataverse:dv-connect`
- Project repository layout → `ppbp-overview`
